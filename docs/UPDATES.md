# 更新与回退

管理员点击版本徽标打开 **版本与更新**，检查正式版本、安排更新或回退。Lite / Pro 均支持本机维护；Pro 还能从 **群站管理** 对已接入的子站发起版本操作。更新会短暂重启服务，建议先保存完整备份并安排维护窗口。

0.41.0 起，执行器按受保护部署身份选择 Docker、原生专属网关或历史 Nginx 路径，保留现有后端与公网入口，不会在升级时把原生站点改为 Docker。新安装与已有部署升级是不同操作，不能用一键安装覆盖在用数据。

子站实际切换由其本机 Unix socket 更新器执行，没有公网更新器端口。旧主动拉取式轻量业务站没有这一群站版本入口，由服务器管理员使用匹配的升级工具维护。

## 群站版本管理

在 Pro 主站的群站管理中展开子站的 **版本管理**，会主动向该子站更新器检查正式 Release，并显示当前版本和可回退快照。**检查版本** 每次都重新查询发布来源；后台状态轮询只读取操作状态，不重复查询 GitHub。选择目标版本后，主站会携带当前版本和一次性请求 ID 提交操作；子站校验目标版本、数据库兼容性、安装基线和并发状态后才会执行。

版本操作只允许管理作用域的子站令牌，主站网关仅放行版本状态、检查和应用三个固定路径；只读令牌、任意 URL、查询参数和其他更新器路径都会被拒绝。子站重启期间主站持续读回状态并自动重连，只有操作 ID、成功回执和目标运行版本一致才提示完成。提交响应丢失时保留原操作 ID；确认子站空闲后可重试同一请求，不创建重复操作。结束本地等待不会取消子站已执行的任务。版本切换不会删除子站账号、订阅、配置或流量数据；回退仍受子站本机安装基线和兼容性限制。

## 检测与选择更新

1. 点击 **检查更新**，读取本项目 GitHub 的正式 Release。草稿、预发布及缺少对应 Lite / Pro 版本包的版本不列出；Docker 下载阶段还会校验同版镜像归档与元数据。正式发布需完成全部安装资产上传，未完成的发布不应作为生产更新目标。
2. 紧凑卡片显示当前版本、最新版本和新版本提示。点击 **立即更新** 选择最新正式版本；也可展开 **选择版本与回退**，选择具体版本并点击 **更新到所选版本**。
3. 核对版本后点击 **确认更新**。检查更新本身不会安装，也不会定时自动安装。
4. 后台下载并校验外层 SHA256、包内文件清单、版本与版本类型，以及固定代理核心。随后停服务、备份、切换版本、准备配置并验证服务健康。
5. 面板短暂断开时页面继续重连。确认目标版本已健康运行后开始 **8 秒倒计时**，自动刷新当前页面；不会在固定等待时间结束但服务仍异常时盲目刷新。

版本目录缓存 15 分钟；手动检查绕过缓存，以便发现刚发布或刚上传完整安装包的版本。无法连接版本来源时显示错误并保留已有目录及原检查时间，后续状态读取仍显示来源错误，不把网络故障、空缓存或过期目录当作最新版本。更新目标只能来自有效且未过期的正式目录。下载临时文件在操作结束后清理。发行来源是本项目 GitHub，不能在网页指定任意下载 URL 或执行 shell 命令。

这是后台升级与自动重连，不是进程内无中断代码替换。代理核心可能短暂重启，客户端需要自动重连。旧面板或浏览器页面在更新期间保持打开即可；关闭页面不取消服务器上的操作，重新打开会恢复显示进度。

## 回退范围

**不能回退到安装基线之前。** 新安装把该安装包版本记为基线；升级不会改变它。旧部署在第一次启用此功能时，以升级前正在运行的版本建立基线。这是保守下限，不会推测缺失的更早安装历史。

基线保存在 root 专属的 `/var/lib/guangyue-updater/installation.json`，与面板数据库、面板程序和它们的回退快照分离。网页提交、直接调用 API、普通升级脚本和回退操作均检查下限。服务器 root 管理员有操作系统的最终控制权；此约束不声称能阻止 root 手工替换软件或删除所有安装记录。

回退列表显示最多 30 个已安装且具有本机备份的旧版本，目标必须：

- 不低于安装基线，且低于当前版本。
- 属于相同 Lite / Pro 类型、站点身份和部署角色。
- 与当前数据库迁移清单及校验值兼容。

**手动版本回退保留当前账号、订阅、配置和流量数据库。** 它只切换程序、前端和匹配服务定义。数据库不兼容的版本会被禁用，服务器也会拒绝请求；不会为了满足回退自动恢复几天前的用户或计费数据。准备配置或健康检查失败时，会恢复此次操作开始前的完整快照。

若回退到 0.16.0 等没有版本入口的旧面板，在线更新按钮随旧前端消失；独立更新服务、安装基线和历史继续保留。可通过 SSH 使用下面的受校验安装包升级命令回到新版。回退本身不会删除离线备份，磁盘不足时拒绝开始新操作。

## 安装与运维

标准安装自动配置按需启动的本机 Unix socket 更新服务。主面板保持非 root 身份；维护执行器只提供本机入口，不开放公网端口。原生 socket 为 `/run/guangyue-update.sock`；Docker 使用持久目录中的 `/var/lib/guangyue-maintenance/update.sock` 并在容器内提供受限入口。只有本站管理员或具有管理作用域的已接入主站可以发起版本操作，成员与只读令牌不能执行更新。

- `/opt/guangyue-updater/`：独立执行器，回退旧面板时保留。
- `/var/lib/guangyue-updater/`：root 专属安装基线、版本目录、操作与回退记录。
- `/root/guangyue-backups/`：完整操作前快照；含应用、配置、状态和 PostgreSQL dump（适用时）。Docker 快照另有项目、镜像与 Compose 身份。
- `/etc/guangyue-deployment.json`：新安装的受保护部署身份；不可手动切换后端。
- `/var/lib/guangyue-maintenance/pending`：新部署的持久维护冻结标记。未提交操作完成恢复前仅放行健康检查，不能手工删除。
- `guangyue-updater.socket` / `guangyue-updater.service`：按需启动，空闲约两分钟后退出释放内存；开机检查未完成操作的恢复记录。

迁移服务器时同时备份更新记录、匹配离线备份、面板状态与配置。不要只复制数据库后把旧版本当作新安装来重建下限。删除某个升级备份后对应回退选项不再可用；请保留至少最近一次已知可用备份。

```bash
sudo systemctl status guangyue-updater.socket guangyue-updater.service
sudo python3 /opt/guangyue-updater/update_agent.py status
# 从正式 Release 获取、验证并解压所选安装包后：
sudo python3 /opt/guangyue-updater/update_agent.py install-bundle /root/guangyue-panel-pro-VERSION-linux-amd64
# 目标必须是 status 列出的兼容本机快照；先替换示例版本：
sudo python3 /opt/guangyue-updater/update_agent.py rollback PREVIOUS_VERSION
```

将 `VERSION` / `PREVIOUS_VERSION` 替换为真实版本；不要原样运行占位符。首次安装 0.41.0 的服务器不能回退到 0.40.x。新完整版本包已包含固定代理核心，不必额外下载未知来源二进制。旧版本资产的组件要求见对应版本安装说明。

更新不迁移既有 Nginx 虚拟主机、域名或证书布局；历史站点保留 Certbot 钩子，新站沿专属网关续期。证书部署和升级共用互斥锁。

源码开发环境或非标准目录安装可能显示在线更新服务不可用，需按自身部署方式维护。0.41.0 起受管 Docker 支持应用镜像更新与兼容回退，普通版本更新不暗中替换 PostgreSQL / Redis 镜像。跨架构、更换数据库、原生与 Docker 互转、强制数据库降级和批量业务站升级，均不属于普通版本操作。

## 历史网络策略

旧 Nginx / 业务站路径的网络优化与版本操作互斥，升级保留显式选择。回退到 0.18 或更早版本时，HY2 使用旧版自身策略，系统 BBR 与 UDP 缓冲保持当前值；重新升级到 0.19 后恢复保存的 HY2 选择。0.41.0 新 Docker / 原生专属网关默认保持宿主网络参数，不套用旧安装的默认 BBR 行为。详见 [运维指南](OPERATIONS.md#网络优化的适用范围)。

## 旧 Pro 首次升级到 0.35.1 或更新版本

旧 Pro 的独立更新执行器可能仍使用旧 PostgreSQL 恢复函数。仅下载新程序不能修复正在执行本次升级的旧执行器：如果本次升级先迁移数据库、随后失败或断电，旧函数可能无法完整撤回新增的数据库对象。

**首次升级请使用已验证新安装包中的 `deploy/upgrade.py --apply`，不要只通过旧网页更新按钮或旧执行器的 `install-bundle` 开始这次升级。** 从本项目正式 Release 获取固定版本，核对外层与包内 SHA256，并按该版本的资产说明验证固定代理核心。将可信安装包解压到 root 专属目录；脚本会拒绝不安全的链接、非 root 所有者或可被其他用户写入的恢复工具路径。

```bash
# 以下命令在 root 会话中执行；示例目录须替换为实际已验证安装包。
cd /root/guangyue-panel-pro-0.35.1-linux-amd64
python3 deploy/upgrade.py --bundle "$PWD"
python3 deploy/upgrade.py --bundle "$PWD" --apply
```

不加 `--apply` 只做预检查，不修改独立执行器。正式执行时，命令先获得部署锁、验证安装包并确认没有未完成的更新、恢复或网络操作，再暂停闲置的更新 socket / service。它会再次检查操作记录，把原来的 `infrastructure.py` 备份到 `/var/lib/guangyue-updater/recovery/helper-infrastructure-*/`，同步落盘后原子替换为可信新包中的同名恢复模块，最后重新启动更新 socket。随后才开始常规停面板、备份和升级。因此，升级失败后重新启动的独立执行器也会使用新的恢复函数。

这一步只预置恢复模块，不提前改变 helper 的 `VERSION`、其它脚本、安装基线、历史记录、面板配置或数据库；成功升级后的正常安装流程再更新完整执行器。如果在停止入口前恰好出现并发排队请求，本次命令行维护会拒绝继续，恢复 socket 并保留排队记录，由正常执行器恢复或反馈失败；等待处理结束后重新运行即可。不要手工删除操作日志或强停正在更新的进程来绕过检查。

升级失败时保留已预置的新恢复模块与私有备份，不要把旧恢复模块复制回去。升级完成并确认新版本健康后，后续更新可以继续使用面板中的版本入口。
