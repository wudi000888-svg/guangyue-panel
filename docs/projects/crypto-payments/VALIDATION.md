# 加密钱包验证与后续支付交付计划

版本：1.1。本期已有钱包派生、权限、幂等、并发、备份与恢复测试；完整链上支付矩阵仍待实施。测试仅使用公开助记词向量和临时数据库，没有使用用户真实钱包、主网密钥或付款。

## 当前钱包验证边界

钱包套件为 `crypto_hd_test.go` 与 `crypto_wallet_test.go`，后者在 `TestPostgresBehaviors/crypto_wallet_*` 中注册。覆盖公开 BIP-32/EVM 向量、浏览器 Core 与 Go 公钥/地址一致、管理员与成员隔离、错误密码、秘密不入普通响应/持久重放、重复分支、独立连接并发分配、停用、备份加密/篡改、恢复索引、完整性与快照。无价值测试材料不能发送真实资金。

前端需证明官方 Wallet Core 4.8.4 的 WASM 实际加载并生成向量一致结果，不能只测试手写 mock。资源随本站安装包分发，内容哈希在打包时核验，生产不依赖 Node 或第三方 CDN。只有需要钱包功能时才加载约 10.39 MB WASM，不增加普通登录页的首屏下载。

新站恢复必须 `recovery_required` 并暂停，管理员核对最后使用索引后才允许继续；同站旧备份合并不能降低索引。这只是已知记录内的防复用约束，不能推断旧备份可发现所有跨部署外部使用。钱包验证不覆盖真实链上余额、交易广播、最终确认、订单认款、自动归集或退款。

## 测试分层与隔离

| 层级 | 环境 | 必须证明 |
| --- | --- | --- |
| 领域单元 | Go 任意精度类型、可控时钟、BIP-32 公共测试向量 | 精度、报价、分支路径、状态与幂等指纹，不依赖真实网络 |
| 离线集成 | JSON-RPC fixture、模拟地址服务、SQLite 临时文件 | 收款、重组、分配预留、退款和恢复闭环；数据库断言 |
| Pro 集成 | 一次性 PostgreSQL、Redis | 独立连接/进程竞争、schema 隔离、事务失败；Redis 故障不影响资金事实 |
| 无价值链 | 独立本地 EVM/测试网、测试 Token、签名器沙箱 | 地址可控制、Gas 加注、Token 转出、退款与净到账核对 |
| 前端 | Vitest + 浏览器桌面/手机 | 类型、轮询、断线、刷新恢复、资金域隔离、可访问性 |
| 后续逐链验收 | 独立 RPC、正式资产/确认策略、批准资金控制 | 实际链能力、配置版本、资金转出与限额首单完整证据；另行进入 P3/P4 |

测试和正式环境使用不同数据库、分支、账户、网络指纹及 ID 域。fixture 不包含生产用户、订阅、服务凭证或个人钱包信息；测试网络只有无价值代币。文档示例和模拟 UI 不生成主网可付款二维码。

## 现有回归基线

可复用 [payment_integration_test.go](../../../backend/internal/controlplane/payment_integration_test.go) 的法币收款唯一性、晚付、多付、未知款、配置快照、退款与重启案例；[postgres_test.go](../../../backend/internal/controlplane/postgres_test.go) 注册 Pro 行为套件；[db_test.go](../../../backend/internal/persistence/db_test.go) 覆盖迁移校验、schema 隔离、快照和单控制器。前端 [commerce.test.ts](../../../frontend/src/lib/commerce.test.ts)、[api.test.ts](../../../frontend/src/lib/api.test.ts) 可扩展付款类型和本地请求范围。

这些是法币和基础设施已有测试，不是 crypto 验收。当前部分“跨实例”测试共享 Store、SQLite 为单连接；新增测试必须覆盖真正独立 Store/连接和进程，不用同一个全局锁串行化来证明唯一性。

当前 `app_test.go` 通过 `TestPostgresBehaviors/` 测试名前缀选择 PostgreSQL，单独设置 DSN 后运行普通测试仍可能只测 SQLite。新 crypto 套件须使用显式双后端 harness，并在结果中记录实际 driver；PostgreSQL 为必需的 CI 项不能出现 SKIP 后仍放行。

## Fixture 约定

拟新增 `backend/internal/payments/crypto/testdata/`，按照场景目录组织；本次没有创建这些测试文件。

| 文件类型 | 关键字段 |
| --- | --- |
| `scenario.json` | ID、网络指纹、资产版本、确认策略、固定时钟、输入顺序、故障点、预期金额/claim/funding/权益数量 |
| `rpc-*.json` | 供应商身份、JSON-RPC method/params、完整响应或错误、head/safe/finalized、block/receipt/log 元数据 |
| `branch-*.json` | 规范分支公钥、派生路径、索引、已知 EVM 地址、控制方和高水位；私钥仅使用公共测试向量，不可接入生产签名器 |
| `allocation-*.json` | 请求指纹、池版本、所有者、幂等预留、响应丢失、外部高水位及恢复 checkpoint |
| `expected.json` | 最终事实、用途 claim、付款单总额、责任金额、账本、订单 funding、outbox/消费次数及扫描游标 |

RPC fixture 必须包含完整 receipt；不能只拼日志绕过 receipt 一致性。供应商 quorum 场景要模拟独立来源，而不是两个域名返回同一实例数据。时间以可控时钟推进，CI 不靠长 sleep 或主网出块。

## 核心验收矩阵

完整技术设计有 23 项资金验收用例。以下工程用例负责证明实际落地，必须同时检查 API 行为和数据库不变量。

| ID | 场景与故障注入 | 断言 |
| --- | --- | --- |
| V-01 | 只连接 OKX；拒绝/重复/过期签名；错误域名/链/账户；MPC/未支持智能账户 | 不生成 xpub 或 invoice；挑战单次消费，资金库不静默变化 |
| V-02 | 无效 xpub、硬化子级、重复真实分支、更换 pool ID；多索引独立比对 | 拒绝不合法分支；面板与签名器派生一致，验证 EVM 地址而非 Bitcoin 地址 |
| V-03 | 同一 allocation 请求双进程；服务已预留但响应丢失；同键改参数 | 同键只保留一个预留/付款单，参数冲突明确；请求键在重试时不变化 |
| V-04 | 地址预留后 invoice 提交失败；恢复旧库；高水位大于备份；索引跳过 gap limit | 预留/废弃地址不复用，恢复先核对外部事实；旧地址能完整发现与支出 |
| V-05 | 相同日志由多 RPC、重复通知和重扫投递 100 次 | 一条最终事实、一个用途、一次金额累计；不会认成两笔 |
| V-06 | 同 tx 真实有两条 Transfer；同 invoice 60+40；两 invoice 各足额 | 每条日志独立且仅使用一次；同单一份权益，不误阻断真实两单 |
| V-07 | crypto、余额、易支付、Stripe 同时付同单；不同历史 invoice 竞争 | 唯一 funding、一次权益；额外真实款保留可核对责任 |
| V-08 | 6/18 位金额、uint256 边界、报价取整、非法文本、少付/超付 | 任意精度与规范字符串；前端显示/复制/扫码和后台数量一致，不跨资产求和 |
| V-09 | 错链/假币/同 symbol、revert receipt、零额 spam、自有 Gas/归集款 | 不开通，不把提示或内部流转算成订单收款 |
| V-10 | 两个来源一致/分歧/缺失；L2 inclusion 有但 L1 批次未最终确认 | 只有足够 quorum 和正确最终性证据能结算，不能自动降级 |
| V-11 | 浅重组，日志 100/101 变 101/102；深重组推翻已记账块 | 替换整份规范 receipt 不双计；深重组冻结，证据映射不再认款 |
| V-12 | 截止前上链但截止后发现；交易所长等待；取消/到期后到账 | 及时款继续按原报价，真正晚付/取消款保留责任，不用回调时间猜测 |
| V-13 | claim/账本/funding/outbox 事务中失败；消费后应答前杀进程 | 原子提交或回滚；恢复沿用同一事件，不能再次开通 |
| V-14 | 入款后尚未发货，批准本金退款；另案只退款超付 20/实付 120 | 本金退款阻止旧消息履约；退超付仍允许有效本金 100 开通 |
| V-15 | 同一转出日志核销两笔退款；替换交易；同 tx 两条实际转出日志 | 同一 Transfer 只核销一次；广播/tx hash 不是已退款，可真实分别核销两条日志 |
| V-16 | 停用/撤销池、浏览器断开、换池、服务/RPC/Redis 故障 | 新收款/结算按独立开关暂停；历史监听查询保留，不换地址或低确认兜底 |
| V-17 | SQLite↔PostgreSQL 快照、外键、旧程序/新 schema、迁移 tamper | 所有新增关系保留，checksum 不改；高水位/消费证据缺失时拒绝恢复后自动发单 |
| V-18 | 成员访问他人单、子站 token、伪造租户；选中子站再操作资金配置 | 后端拒绝越权；请求不带远程站点资金上下文，主站资金边界明确 |
| V-19 | 外部已预留但本站 invoice 未提交时刷新；创建应答丢失；已收款/到期后刷新；支付方式与充值 | 接续原持久请求或恢复同一付款单及历史证据，终态不误导继续付款；两创建入口不重复预留，crypto 内嵌且不开放充值 |
| V-20 | 320px 手机/桌面、键盘/读屏、错误网络；仅权益或超付退款状态变化；条件查询 304 | 关键操作可用，不横向溢出/抢焦点；组合视图版本刷新正确，304不解析空JSON，查询失败不冒称付款失败 |

## 并发与崩溃方法

1. 单元与业务集成使用 barriers 驱动真正的竞争，至少两个独立 DB 连接；SQLite 使用同一临时文件的独立 Store，PostgreSQL 使用独立连接池。分别验证同付款权威竞争与不同 site schema 隔离。
2. 正常控制器有独占保护，不能为测试擅自放宽生产单控制器规则。在服务/仓储层验证数据库约束，进程重启则走正常控制器恢复路径；需要多 worker 的链任务验证 fencing 与租约交接。
3. 注入事务各写入点的 error，验证全回滚；另以子进程完成外部预留或提交后强制终止，再启动恢复进程，验证持久记录而不是只重建内存 App。
4. 固定请求、事件与分配键，恢复后比较数据库基数、按资产的金额平衡、订单权益版本、外部高水位和退款责任；仅检查 HTTP 200 不算通过。
5. 不支持各站共享收款分支，测试服务必须拒绝重复归属；如果以后增加中心 claim，需要新的跨 schema/跨部署套件，不能把本站 UNIQUE 当成完成证明。

## 实施后的验证命令

以下为仓库现有验证入口，列出不等于本轮已执行。Go/Node 版本见 [CONTRIBUTING](../../../CONTRIBUTING.md)。开发 crypto 测试须先实际增加到对应包，不能让没有匹配测试的 `-run` 输出充当成功。

```bash
cd backend
go test -race ./internal/controlplane -run '^Test(Payment|Epay|Stripe|Commerce)' -count=1
go test -race ./... -count=1
go vet ./...
```

```bash
cd frontend
npm ci --ignore-scripts
npm test
npm run build
```

完整代码交付执行仓库根目录 `bash scripts/check.sh`。Pro 配置一次性测试数据库的 `GY_TEST_POSTGRES_DSN` 和 Redis 的 `GY_TEST_REDIS_URL` 后，运行完整套件；缺失环境导致的 skip 必须单列，不能写成 PostgreSQL/Redis 已通过。CI 使用 PostgreSQL 17、Redis 8、Go 1.26.8、Node 24。部署相关验证在 Linux/OpenSSL 3 环境运行，macOS LibreSSL 的限制见开发指南。

2026-10-08 本机使用 Go 1.26.8、Node 24.19.0，并在临时目录从官方源码编译 PostgreSQL 17.11 与 Redis 8.10.2，仅绑定 loopback、独立端口和密码，不安装系统服务。数据库验证明确设置 `GY_TEST_POSTGRES_DSN` / `GY_TEST_REDIS_URL`。本机数据卷不足 10% 空闲会触发既有工单图片磁盘保护，因此该回归使用一次性 4 GiB 稀疏测试卷作为 `TMPDIR`，没有放宽生产磁盘门槛。具体通过结果以本次提交的实际测试记录和 CI 为准；没有执行 Anvil/Geth 或主网资金测试。

## 交付证据与发布门槛

每个施工任务记录基线/目标 commit、实际命令、环境、通过/失败/跳过、fixture ID、数据库不变量结果，以及尚未验证的能力。文档更新、SQL 语法验证、模拟付款和真实网络验收必须分别标记，不能混称“支付已工作”。

| 门槛 | 放行要求 |
| --- | --- |
| 领域/内核提交 | 新约束及法币回归通过，跨渠道竞争、失败恢复与退款准入形成证据 |
| 沙箱预开发 | 无价值完整闭环，分配/收款/Gas/归集/退款/恢复可复现；默认生产入口停用 |
| 正式配置 | 逐链资产、独立 RPC、finality、签名器/手工支出方案、高水位备份与预算验收 |
| 受控首单 | 限额开启单一已验收资产，最终收款→唯一开通→批准归集净到账→账目核对完整 |
| 版本发布 | 同步应用版本与变更记录，现有检查和安装/升级验收通过，Lite/Pro 安装包、校验和及 SBOM 上传并核对后发布 |

发生深重组、金额不平衡、地址重复、资金控制/恢复证据缺失时停止新收款和自动资金动作，保留历史查询及责任记录。升级后的新迁移不允许直接回退到无法读取当前 schema 的旧程序；恢复备份还要核对外部资金与地址高水位，不能只回滚本地数据库。
