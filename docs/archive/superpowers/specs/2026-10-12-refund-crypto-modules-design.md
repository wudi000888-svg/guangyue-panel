# 退款权益与加密货币模块设计

## 目标

允许订单在套餐策略发生后续变化后仍能安全申请和审批退款，同时保持多套餐权益的排队顺序；将加密货币支付从普通交易设置中拆成独立、可理解且可审计的管理模块。

## 当前问题

- `commerce_orders.go` 用 `Entitlement.Revision == Order.AppliedRevision` 判断退款资格。套餐节点、协议或倍率调整会更新权益版本，导致原本可退款的订单被错误拒绝。
- `PlanSlot` 和当前 `Entitlement` 没有订单来源标识。A→B→C 后无法在队列中精确定位 B，也无法只撤销目标订单的权益。
- 活跃订单退款当前先把到期时间置为现在，再由周期任务异步恢复队列，期间可能短暂无权限，且撤权目标不够明确。
- 加密货币设置、钱包、归集和法币支付共用交易设置页面，用户难以区分支付配置、钱包保管和资金操作。

## 设计

### 1. 订单权益来源与退款

为 `domain.Entitlement` 和 `domain.PlanSlot` 增加可选的 `SourceOrderID`。购买订单完成开通时写入订单 ID，暂停当前权益生成队列槽位时继承来源 ID；人工调整或历史数据没有来源 ID。

退款申请记录目标订单的权益来源和申请时用量快照。套餐策略 Revision 只保留为审计字段，不再阻断退款。退款事务必须重新读取并锁定订单与用户文档，使用订单状态、权益来源 ID 和用户文档版本做 compare-and-swap，避免覆盖并发购买或人工调整。

- 目标是当前权益：订单进入 `refunding`，等待业务站/子站撤权 barrier 完成；撤权完成后恢复最近的未退款队列槽位，原子更新用户、订单和退款申请状态。
- 目标在队列：按 `SourceOrderID` 删除该槽位，其他槽位顺序、到期时间和流量快照不变，不经过 `PendingReset`。
- 续费订单：仅回滚该订单增加的有效期；后续购买或策略更新不被覆盖。
- 无来源 ID 的历史或人工权益：进入人工对账分支，不自动猜测撤权目标。

退款金额按订单剩余权益计算，已消耗流量不退款；管理员审批时可以降低退款金额，但不能超过剩余可退金额。余额退款在同一数据库事务内入账；Stripe 继续使用原路退款队列，易支付和加密货币必须记录真实外部转出结果后才标记成功。所有状态变更带操作 ID，重复请求只返回第一次结果。

### 2. 独立加密货币模块

新增一级路由 `/crypto-payments`，管理员侧边栏显示“加密货币”。页面拆为三个工作区：

1. **支付配置**：总开关、支持链/币种、RPC/最终性、汇率、发票状态和异常付款。
2. **钱包与地址**：HD 钱包、xpub/外部公钥、订单地址、备份与风险提示。私钥继续由 Vault 加密保存，地址不复用。
3. **资金归集**：按链/钱包显示余额和 Gas、归集地址、费用预估、任务状态和重试。

普通“交易与接入”仅保留法币支付配置和加密模块跳转卡片；用户订单中的加密付款组件保持原付款流程，但链接到独立的支付状态和发票详情。后端 API 先复用现有 `/api/commerce/crypto/*`，前端通过独立容器隔离权限和状态；所有操作继续要求管理员权限、密码重认证和 `operation_id` 幂等。

## 错误处理与安全

- 退款找不到来源订单、权益已被人工替换或 CAS 失败时返回“需要人工对账”，不自动撤销其他套餐。
- 链上退款不复用法币 `payment_refunds`，使用独立链上转账状态并以订单、链、资产和交易哈希幂等。
- 页面轮询只刷新当前工作区，操作成功、失败、排队和等待确认均显示明确状态。

## 验证

- 后端测试覆盖套餐策略编辑后退款、A→B→C 退当前/中间/最旧队列、并发重复审批、子站撤权 barrier 和剩余额度计算。
- 前端测试覆盖独立加密货币入口、工作区切换、普通交易设置不再渲染钱包配置、移动端布局。
- 完整 Go race/vet、Vitest、vue-tsc、生产构建和 GitHub Lite/Pro 安装矩阵必须通过后再发布。
